## 0. 一页看懂

- **生产实例**：同一台 VPS 上，本仓库的第二个检出目录，自己的 `.env`（`CORE_ENV=production`、生产库）。
  - compose 项目名、网络名、别名**都只由 `CORE_ENV` 决定**，compose 文件里这些变量不给默认值，不经实例片段的 compose 命令直接报错；
  - 生产 Core 不挂共享的 `data_net`，只挂一条专用数据网络和一条只给 Inventory 的内部网络（契约 §10 第 5 条“网络上互不可达”，P-07）。
- **部署**：合并到 main 照旧自动部署 Demo 实例。生产实例由人手工触发同一个工作流升级：选“生产”、填 SHA。生产部署在迁移前先备份本库（P-01、P-09）。
- **W7a 已有的**：infra_mysql 每晚全量逻辑备份到 R2，保留 30 天，做过一次还原演练（`vps_infra/backup/`）。binlog 已开，本机保留 3 天。
- **W7a 还缺的**：
  - binlog 每 4 分钟传一次到 R2，按服务器身份与启用批次分路径，能发现缺号与撞名；
  - 每晚加一份单快照、记 binlog 位置与服务器身份的全量导出；
  - 整机恢复的运行手册（含 Core 与 Inventory 的专门步骤）；
  - 传输与每晚备份的告警；
  - 上线前在另一台机器上演练一次。
- **心跳检查**：只用计费平台腾出的 3 个免费位置（P-03）：生产实例 2 个（`readyz` 并入定时任务状态、`invariants`），备份 1 个（binlog 传输加每晚备份）；Demo 实例不再推心跳。
- **登记到本仓库的编号任务**只有本仓库里的改动（部署脚本、工作流、运行手册）；`vps_infra` 的改动与由人做的步骤另列（第 4 节）。

## 1. 生产实例

### 1.1 服务器上的布局

| 项 | Demo 实例（现状） | 生产实例（新） |
| --- | --- | --- |
| 检出目录 | GitHub secret `VPS_APP_DIR` | 新 secret `VPS_APP_DIR_PRODUCTION`，另一个目录 |
| `.env` | `CORE_ENV=demo`、Demo 库 | `CORE_ENV=production`、生产库（infra_mysql 里新建的独立库与账号） |
| compose 项目名 | `acuven_stock_core` | `acuven_stock_core_production` |
| 调用方用的内部网络 | `stock_core_net`（与 Demo 网店共用），别名 `core_api` | `stock_core_production_net`，只给 Inventory 用；生产 Core 在这条网上的别名是 `stock_core_production`，Inventory 只用这个名字 |
| 数据网络 | `data_net`（与网店等共用） | `infra_mysql_core_production_net`（`--internal`）：只有 infra_mysql 与生产 Core 两个成员（P-07）。infra_mysql 用 `docker network connect --alias mysql` 接上，所以连接串里的主机名照旧是 `mysql` |
| 凭据 | Demo 网店的业务凭据、运维凭据 | Inventory 的业务凭据。运维凭据一个，下面两个令牌：巡检一个、Inventory 每日对账一个，分开轮换与吊销（§10 第 2、4 条） |
| 心跳检查 | 不推（契约 0.20） | `stock_core production readyz`（含定时任务状态）、`stock_core production invariants`（契约 0.20） |

**为什么不让生产 Core 挂 `data_net`**：
- 网店后端也在 `data_net` 上（`acuven-shop` 的 compose）。Inventory 要连 infra_mysql，也会挂上去。Core 的 uvicorn 绑在 `0.0.0.0`，挂在 `data_net` 上就等于这些容器都能直连生产 Core。
- 两个实例在 `data_net` 上都叫 `core_api`。调用方同时挂在自己的内部网络和 `data_net` 上时，按 `core_api` 解析到哪个实例并不可靠。

Demo 实例不变（它本来就是演示数据）。

### 1.2 本仓库要改的地方

1. **实例片段 `deploy/instance.sh`**（新增，被其他脚本 `source`）：
   - 按固定规则从检出目录的 `.env` 只读 `CORE_ENV` 一个键，**不 `source` 整个文件**（同 §8.5）。值只接受 `demo` 或 `production`，严格匹配，不去空格、不认引号与行尾注释；别的值一律失败。
   - 由它给出 compose 项目名、网络名与别名（两个实例都给出具体值，Demo 取现在的值）。之后所有 compose 调用一律带 `-p <项目名>`，网络名与别名经环境变量传给 compose。
   - **不另设 `COMPOSE_PROJECT_NAME`、`CORE_INTERNAL_NETWORK` 之类的键**：多一个键就多一种漏配。
   - 另提供“找到本实例的 `core_api` 容器”的函数：按 compose 项目标签找，再核对标签 `com.docker.compose.project.working_dir` 与当前检出目录相同（两边都先 `realpath`），并排除一次性容器。
     健康检查、巡检、运行手册里的开通与签发、恢复时起服务，都只经它找容器。
2. **`docker-compose.yml`**：
   - 网络名与别名写成 `${变量:?…}`，**不给默认值**。不经 `instance.sh` 的手工 compose 命令会直接报错，不会悄悄落到 Demo 的名字上；
   - 生产时不挂 `data_net`，改挂专用数据网络。Demo 与生产挂的网络集合不同，用 compose 的 profile 或两个小的覆盖文件实现，由实施任务定，验收看第 6 节。
3. **`deploy/deploy.sh`**：
   - 先 `source deploy/instance.sh`；
   - 建调用方内部网络用它给的名字。生产的专用数据网络由 `vps_infra` 建（第 4 节），不存在就失败，不自己建；
   - 清旧镜像仍按 `acuven.project=stock_core` 标签。prune 只在成功路径、换完容器之后跑，不清任何容器（含已停的）正在用的镜像；主机锁保证两个实例的部署串行；
   - 主机锁里写的持锁方带实例名（`stock_core demo` / `stock_core production`）；
   - **生产实例在迁移前先备份本库**（P-09）：
     - 怎么导：经 `docker exec infra_mysql` 用 infra_mysql 容器自己的 root（取自它的环境变量）跑 `mysqldump --single-transaction --no-tablespaces --set-gtid-purged=OFF --databases <生产库>`，**不加** `--source-data`（不加全局读锁）；
     - 怎么核对：照每晚备份核对文件末尾的 `Dump completed`；
     - 放在哪：检出目录之外的固定目录，权限 600，脚本只保留最近 5 份；
     - 失败怎么办：以失败结束，什么也不改（D3）。
     这是有意的耦合：依赖 infra_mysql 的容器名与环境变量名，与 `vps_infra/backup/` 同一做法，部署用户本来就有 docker 权限，没有新增权限；
   - 超时预算：生产库很小，备份按 1 分钟上限算。`deploy.yml` 的 `command_timeout` 与 job 超时随之重算，写进 067。
4. **`deploy/healthcheck.sh` 与 `deploy/monitor.sh`**（后者由 CORE-TASK-065 新建、066 改为契约 0.20）：都 `source deploy/instance.sh`，经它找本实例的容器；找不到或不止一个就算没查成。
5. **`.github/workflows/deploy.yml`**：
   - **输入**：手工触发多一个输入 `instance`（`type: choice`，`demo` / `production`，默认 `demo`）。推送触发的部署只部署 Demo，D1–D5 与 `on:` 的形状约束不变；
   - **目录**：在 shell 里解析：选了生产而 `VPS_APP_DIR_PRODUCTION` 为空，`exit 1`。不用 `a && b || c` 这类会静默回落的表达式；部署与上线后健康检查两步用同一个解析出的目录；
   - **拒绝旧 SHA**：选了生产时，远端在 `git fetch` 之后、`git checkout` 之前，用 `git merge-base --is-ancestor <067 的合并提交> "$DEPLOY_SHA"` 核对。不满足就退出，不动检出（检出停在旧提交上的话，cron 的巡检会跑旧脚本）；
   - **并发组**：按实例分开，`deploy-${{ inputs.instance || 'demo' }}`。共用一个组时，排队中的生产手工运行会被新的推送静默取消，或者反过来；跨实例的串行交给主机部署锁；
   - 文件头“生产实例等真实网店定了再加”那句改掉。
6. **运行手册**：新文件 `docs/PRODUCTION_RUNBOOK.md`，写生产实例首次上线、升级与回滚的界线（第 1.3、1.4 节）、整机恢复（第 2.4 节）与演练（第 2.5 节）。§8.5 的巡检手册仍是 CORE-TASK-065 的 `docs/OPS_MONITORING.md`，生产实例的检查装法并进那里。

### 1.3 首次上线（由人做，按运行手册）

1. 在 infra_mysql 建生产库与账号，照 `vps_infra/scripts/provision-project.sh`。它授本库全部权限，在终端打印一次密码；它打印的连接串主机名是 `mysql`，与专用数据网络上的别名一致。它还会分 Redis 段，Core 用不上。
2. `vps_infra` 建专用数据网络并把 infra_mysql 接上（第 4 节）。
3. 在服务器上克隆本仓库到生产检出目录，写 `.env`（`CORE_ENV=production`、生产库连接串），之后按 §8.5 加运维令牌与心跳地址。GitHub 上加 secret `VPS_APP_DIR_PRODUCTION`。
4. 手工触发部署，实例选“生产”，填当前 main 的 SHA。用 `docker compose ls` 核对两个项目都在。
5. 经 `instance.sh` 找到生产的容器，用里面的命令行开通租户、地点、池、销售入口（入口名 Inventory），签发 Inventory 的业务凭据，以及运维凭据下的两个令牌。令牌只在终端出现一次，直接写进 Inventory 服务器的密钥文件与巡检的 `.env`。
6. 真实期初之前：
   - W7a 第 2.5 节的演练通过（契约 §12.1 第 7 条）；
   - 第 2.6 节的心跳检查已建好并演练过；
   - 在服务器上用 `SHOW VARIABLES` 核对 `binlog_format=ROW`、`binlog_row_image=FULL`、`gtid_mode=OFF`（现在只是依赖默认值，未核对）；
   - 用 `free`、`df` 核对内存与磁盘余量（P-02）。

### 1.4 升级与回滚的界线（运行手册）

- **升级前**：列出“生产当前 SHA → 目标 SHA”之间的迁移。按 §12.1 第 5 条“先加后删”，任何“删”的那一段，都要它对应的“加”那一段已经在生产上跑过一次；否则先把生产升到中间那个提交。
- **触发时机**：没有 Demo 部署在跑时才触发生产。并发组分开后，两个运行只靠主机锁串行；生产部署（含迁移前备份）持锁较久，同时到来的 Demo 推送部署可能等不到锁而失败，OpenClaw 会把那次合并判为部署失败。
- **回滚**：只能回到上一个好的 SHA，并且不早于第 1.2 节实例片段进库的那个提交（工作流会拒绝）。已经跑过的迁移不倒退。

## 2. W7a 备份与恢复

### 2.1 已有的（`vps_infra`）

- **每晚备份**：每晚 02:47（马来西亚时间）对 infra_mysql 的每个业务库**分别** `mysqldump --single-transaction`，再加一份账号与授权；打成一个 tar，用 rclone 传到 R2 的桶，路径 `infra_mysql/YYYY/MM/…`。
- **保留**：R2 用桶的生命周期规则 `expire-30d`，VPS 本机保留 7 天。这条规则是否覆盖桶里的其他前缀，**未核实**，上线时在 R2 控制台核对。2026-11-19 做过一次还原演练。
- **binlog**：infra_mysql 开着 binlog，本机保留 3 天（`--binlog-expire-logs-seconds=259200`），单个文件上限 256M。binlog 在命名卷 `mysql_data` 里，主机上的部署用户读不到卷目录。
- **初始化脚本**：infra_mysql 第一次启动时，`mysql/init/00-init.sql` 用占位密码建 `erp_app` 与 `claude_ro` 两个账号。

### 2.2 binlog 每 4 分钟传到 R2（`vps_infra` 新增）

- **为什么要主动切文件**：binlog 写满 256M 才换下一个文件，这台机器一天只写几 MB 到几十 MB，一个文件几天都写不满。只传“已写完的文件”，做不到 5 分钟。
- **周期**：每 4 分钟一次（`*/4`）。契约要求丢失窗口本身不超过 5 分钟（§0、§12.1 第 7 条），每 5 分钟一次再加上传用时会超。
- **路径**：`infra_mysql_binlog/<server_uuid>/<批次>/<文件名>`。
  - `server_uuid` 取 MySQL 的 `@@server_uuid`；`<批次>` 是这台服务器启用 binlog 上传的时刻（UTC，例如 `20261125T0300Z`），写在本机的上传配置里。
  - 重建卷或换机器，`server_uuid` 会变；`RESET MASTER` 不换 `server_uuid`，但序号会从 `binlog.000001` 重来，这时由人换一个新批次。两种情况都不会覆盖旧的文件。
- **做法**：服务器 cron 跑一个脚本，以部署用户（有 docker 权限、无 root）运行，每一步都限时：
  1. 在 infra_mysql 里 `FLUSH BINARY LOGS`，把当前文件关掉；读 `@@server_uuid`，与上传配置里记的不同就失败告警，不上传（换了卷或机器，要先换批次）；
  2. `SHOW BINARY LOGS` 列出文件，去掉最后一个（正在写的）与 `binlog.index`，得到已关闭的文件；
  3. 对照本机按 `<server_uuid>/<批次>/<文件名>` 记的“已上传”清单，挑出新关闭的文件：
     - **撞名**：新文件序号不大于本批次已上传的最大序号，失败告警，不上传，要人换批次（多半是 `RESET MASTER`）；
     - **永久缺口**：本批次应传的下一个序号已不在 `SHOW BINARY LOGS` 里（中断超过本机保留的 3 天，被 MySQL 清掉了），失败告警，正文写明永久缺口。这之后要立即做一次全量导出，并换新批次；
  4. 经 `docker exec … cat` 把新文件读到本机中转目录；
  5. 逐个用 `rclone copyto --immutable` 上传：只传新文件，不遍历远端，不靠修改时间比较；远端已有同名而内容不同就失败，不覆盖。上传后照每晚备份的做法核对远端大小，一致才记进“已上传”清单、删掉中转副本；
  6. 成功推心跳，失败或超时推失败（第 2.6 节）。
- **体量**：每天约 360 个小文件，R2 同样保留 30 天（生命周期规则要覆盖这个前缀）。本机 binlog 仍保留 3 天，短时间中断后能补传。
- **不选** `mysqlbinlog --read-from-remote-server --stop-never` 持续拉取：丢失窗口能到秒级，但要多一个常驻进程、断线重连和它自己的监控，V1 不需要。
- 脚本与 cron 文件放 `vps_infra/backup/`，与每晚备份共用 R2 凭据与日志目录，各用各的锁：每晚备份那几分钟里 binlog 不停传。

### 2.3 每晚加一份时间点恢复用的全量导出（`vps_infra` 修改，P-08）

- **为什么**：时间点恢复是“全量备份＋重放它之后的 binlog”。现在每个库分别导出、都不记位置，有三个问题：
  - 各库对应 binlog 的不同位置；
  - 按库过滤重放（`mysqlbinlog --database`）时，DDL 与账号语句按“默认库”过滤，`CREATE USER`、`GRANT` 这类没有默认库的语句会被全部滤掉；
  - 账号文件在最后导出、也不记位置。
- **做法**（建议，P-08）：
  1. 先导出账号与授权（同现在的做法）；
  2. 再做一次 `mysqldump --single-transaction --source-data=2 --databases <全部业务库>`：同一个快照、只有一个 binlog 位置，写在导出文件开头的注释里；
  3. 同时把 `SELECT @@server_uuid` 与当前批次写进 tar 里的一个小文件，恢复时按它选 binlog 的路径；
  4. 现有按库导出保留，单库还原时用。三样都传 R2。全部业务库的大小**未核实**，以 11-19 那次备份的 tar 大小为准，演练时记下。
- **重放时**：不加 `--database` 过滤，整段 binlog 从这个位置起按顺序重放，DDL 与账号变更都能正确恢复。
- **已知限制**：账号导出在全量导出之前、不记位置，两次导出之间（凌晨几秒到几分钟）的账号变更既不在账号文件里、也不在重放范围内，会丢；发生概率很低，接受，写进还原说明。
- **还原账号**：新机器第一次启动 infra_mysql 时**不挂** `mysql/init/`，免得建出占位密码的账号。导入账号文件时，每个账号先删后建，再按导出的密码哈希授权。
- **锁**：`--source-data` 会短暂加一次全局读锁取位置，要等实例上正在跑的长查询结束，等待期间全实例的写入都被挡住。凌晨写入很少，预计很快，**未实测**；演练与上线后核对每晚备份日志里的用时。备份用 root，权限够。

### 2.4 整机恢复的步骤（运行手册）

按契约 §12.1 第 3 条，从“新开一台机器”开始计时，到“调用方补交、对账完成”为止，目标 4 小时内。命令写进运行手册。

1. **开机器、取密钥**：开新机器，装 Docker；从密码管理器取回重建要用的密钥（P-05 的清单）。
2. **起基础设施**：从 `vps_infra` 起 infra_mysql（不挂 `mysql/init/`）、nginx、redis，建网络。
3. **导入全量**：从 R2 取最近一份时间点恢复用的全量导出、它记的 `server_uuid` 与批次、账号文件；先导账号（先删后建），再导全量。
4. **重放 binlog**：从 R2 取该 `server_uuid`、该批次下、导出位置之后的全部 binlog，用一次 `mysqlbinlog --start-position=<位置> <起始文件> <之后的全部文件>` 按序号顺序重放，不加库过滤；`gtid_mode` 为 OFF，按位置恢复。
5. **Core 专门步骤**（契约 §2.5、§12.1 第 3 条）：两个实例的库，各把 `catalog_changes` 的自增起点调到恢复后的最大 `id` 加 1,000,000（表为空时按 0 算），用 `SHOW CREATE TABLE` 核对。**调完之后不能再重放 binlog**：后来又找到更多 binlog 也不能补。
6. **先把新机器保护起来**：在开放任何写入之前，做一次全量导出（第 2.3 节）。上传配置记下新的 `server_uuid` 与新批次，启用 binlog 上传 cron 与每晚备份。
   之后的补交、补录可能要几个小时，这段时间的写入要有异地备份。
7. **起 Core 与调用方**：
   - **SHA**：用最后一次成功的生产手工部署运行里的 SHA（生产落后 main，不用 main）；Demo 用 main。
   - **怎么部署**：在新机器上从 GitHub 克隆检出，按 P-05 重写 `.env`，直接在机器上跑 `deploy/deploy.sh`（工作流的 secrets 还指着旧机器）；改 GitHub secrets（`VPS_HOST`、`VPS_FINGERPRINT` 等）放到最后一步。两种部署都计入用时。
   - **令牌**：丢了就在原凭据下签发新令牌，不换新凭据。换凭据会改变幂等作用域（§10 第 4 条），调用方就没法按原键补交“结果未知”的命令。
   - 再起网店、Inventory 等调用方。
8. **补交与补录**（§12.1 第 4 条）：
   - 调用方补交“结果未知”的命令，补录丢失窗口：网店按支付记录；Inventory 按两个平台的订单补拉，人工模式下由管理员重新核对卖家后台、在 Inventory 重新登记；
   - 网店与 Inventory 都用 `GET /v1/skus?ids=…` 重读映射，Core 查不到的 SKU 标为待处理；
   - 然后对账，跑一次不变量自查。
9. **收尾**：DNS 与 Cloudflare 指到新机器，改 GitHub secrets；记下每一步的用时。

**误操作恢复**（§12.1 第 6 条）走另一条路，不在线上做。不加过滤的整段重放，会把所有库都退回误操作之前，所以：
- 在一台临时实例上按第 3、4 步恢复，第 4 步用 `--stop-position`（先在 binlog 里找到误操作那条事件）或 `--stop-datetime` 停在误操作之前；
- 再只把受影响的库导出、搬回线上；
- 第 5 步只对搬回的 Core 库做。
- **时区**：`--stop-datetime` 按 mysqlbinlog 进程所在的时区解释（infra_mysql 容器是马来西亚时间），而库里时间是 UTC（`--default-time-zone=+00:00`）；运行手册里统一用 UTC，运行 mysqlbinlog 时设 `TZ=UTC`。

### 2.5 演练（上线前一次，之后每季度一次）

- **在另一台机器上演练**（契约 §12.1 第 7 条）：临时开一台云主机，按第 2.4 节第 1–8 步从零恢复，演练完删掉（P-06）。第 8 步用 Demo 网店与一套演练用的 Inventory 配置走一遍，不连线上的平台。
- **量丢失窗口**：
  - 演练前在 infra_mysql 里建一个只为演练用的库，cron 每分钟写一行当时的 UTC 时间（标记表）；
  - 选一个时刻 T（UTC）当作“机器损坏”，只用 T 之前已经传到 R2 的对象恢复（先记下 T 时 R2 的对象清单）；
  - 恢复出的最后一行标记时间与 T 相差不超过 5 分钟。

  这台机器业务写入很少，只看最后一条业务事件量不出上传节奏，所以用标记表。
- **核对项**：丢失窗口 ≤5 分钟；第 1–8 步总用时 ≤4 小时；Core 生产库的行数对得上，不变量自查 `ok`；`catalog_changes` 自增起点核对通过。
- **演练时不动线上**：
  - 演练机不改 DNS，不装任何 cron，`.env` 里不填心跳地址（演练机推成功会把线上真实的故障遮住）；
  - 只起 Core 和第 8 步要用的调用方，它们的外发凭据（平台、支付、短信、邮件、WhatsApp、Telegram）一律换成假值；
  - 读 R2 用一个**只读令牌**（现在没有，要新建，第 4 节）。
- **记录**：写进 `docs/PRODUCTION_RUNBOOK.md` 的“演练记录”一节：日期、执行人、各步用时、丢失窗口、发现的问题。

### 2.6 告警

- **一个检查 `infra_mysql backup`**（P-03），只由 binlog 上传脚本推，周期 4 分钟、宽限 1 分钟：
  - binlog：cron 没跑或脚本卡死时 5 分钟内告警（§12.1 第 2 条“超过 5 分钟没传成功就告警”）；上传失败、撞名、永久缺口当轮推失败；
  - 每晚备份：同一个脚本每轮顺带核对最近一次每晚备份（含时间点恢复用的全量导出）在 26 小时内成功上传（读每晚备份成功时写下的标记文件）；超时就推失败，正文写明是每晚备份。
    现在只有 08:30 每日巡检简报里带上日志的最后几行，那不是告警（§8.5 把备份状态留给本项另做）。
- **一轮的总用时上限 45 秒**：上传积压时每轮最多传一批（例如 20 个文件），剩下的留给下一轮。心跳在一轮结束时推，相邻两次推送的间隔因此不超过 4 分 45 秒，宽限 1 分钟不会误报。
- **合用一个检查的问题**：心跳服务只在状态变化时通知。一晚备份失败会让检查红将近一天，这期间 binlog 中断就不会通知到人。所以照契约 0.20 §8.5 的做法**重新通知**：脚本记下上一轮推出的问题，检查已红而出现新的问题时、或读不出上一轮的记录而本轮有问题时，先推成功、再推失败；运行手册规定只因每晚备份红着时当天手工重跑一次。由同一个脚本推，不违反 §8.5“两个脚本不往同一个检查推”。

## 6. 验收

- **两个实例同机运行**：
  - `docker compose ls` 两个项目都在；
  - Demo 的部署不受影响（Demo 不装巡检，契约 0.20）；
  - 生产实例的健康检查、巡检、开通与签发只认自己检出目录的容器；
  - 生产 Core 在 `data_net` 上不可达，在 `stock_core_production_net` 上只能经别名找到。
- **写错配置**：`CORE_ENV` 缺失、写错、带引号空格或注释时，部署与巡检都失败、不碰任何容器；不经实例片段的 compose 命令报错。
- **手工触发生产部署**：
  - 部署的是填入的 SHA；目录 secret 为空时失败；
  - SHA 早于实例片段的提交时拒绝，检出不动；
  - 迁移前备份失败时什么也不改；
  - 失败、回滚都以失败结束；
  - 推送触发的部署只动 Demo，生产与 Demo 的运行不会互相取消。
- **binlog 传输**：
  - 停掉 cron 后 5 分钟内告警，上传失败当轮告警；
  - 恢复后补传，同一 `server_uuid`、同一批次下序号连续，不重传已上传的文件；
  - 撞名与永久缺口都报失败、不覆盖；
  - 每晚的时间点恢复导出带 binlog 位置、`server_uuid` 与批次；
  - 每晚备份超过 26 小时没成功时推失败；检查已红时出现新问题会重新通知。
- **演练**按第 2.5 节通过，记录写进运行手册。之后每季度一次，备份方式或数据库拓扑变化后加做一次。
