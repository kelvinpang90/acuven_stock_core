## 二、设计细节（可以在批准时一并定，也可接受建议默认）

| 编号 | 问题 | 建议默认 |
| --- | --- | --- |
| Q-01 | 真实网店的商品是否沿用 Demo 里的商品资料？ | 不沿用数量；商品身份只有真实在卖的才建。Demo 商品不进生产 Core |
| Q-04 | 稳定 ID 格式 | 类型前缀＋ULID（`sku_01J…`），不透明、不复用 |
| Q-05 | Core 的“基本名称”用哪种语言？（网店是多语言，见盘点） | 英文一份；多语言展示名留网店 |
| Q-06 | 改过的 SKU 编码，旧值能否给别的 SKU 用？ | 永久保留，不复用（简单、可追溯） |
| Q-07 | 批量导入有错误行时 | 有任何错误行就不允许确认，修好再导（整批原子） |
| Q-08 | 目录变更通知网店的方式 | V1 网店定时拉取变更流；不做推送 |
| Q-09 | 期初导入后发现整批错了，怎么重建？ | 池切 `live` 前可作废重导；`live` 后只能逐 SKU 盘点更正，不开放“重建期初” |
| Q-10 | 流水、幂等记录、审计的保留期 | 流水与幂等记录永久保留（V1 规模小）；安全日志 1 年 |
| Q-11 | 网店用一个还是两个 Core 服务身份 | 两个：前台（预留/确认/查可售）与后台（目录、库存管理、发货/退款/退货） |
| Q-12 | 网店↔Core 的网络与加密；Core 没有公网入口时 `deploy.yml` 的健康检查怎么做 | 同机：仅内部容器网络＋TLS；跨机：加密隧道（与控制面已用的方案一致）。健康检查在部署主机本机执行并比对 commit SHA |
| Q-13 | Core 的 `sku_code` 从哪来 | 网店 `product_variants.sku` 已全站唯一（String 64），直接作为初值；运营之后可在 Core 改（留旧值审计） |
| Q-16 | 整机故障恢复演练频率 | 上线前 1 次；之后每季度 1 次，以及每次数据库拓扑变化后 |
| Q-25 | 网店什么时候开始引入 `StockGateway`？ | 设计批准后先登记一个**纯重构**的 SHOP-TASK：把现有库存读写收拢到 `StockGateway`＋`DemoLocalStockGateway`，行为不变。这一步不依赖 Core，可与节日促销等 Demo 任务交错由 Worker 执行；真正接 Core 等 Core 可用后再做 |
| Q-26 | 晚到支付缺货（ORD-03）在网店后台怎么处理：只给“退款”还是也给“等补货” | 两者都给；补货后由管理员手动点“重试确认”，Core 不自动补扣 |
| Q-27 | 网店现有的每顾客未付款订单上限、促销/活动限量等规则（见盘点）保留在网店还是交给 Core | 留在网店：它们是销售政策，不是实物数量；Core 只管实物可售量 |
